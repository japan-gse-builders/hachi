## 1. 何を作ったか

Hachi は、日本に住む英語話者の高齢者に**毎日 1 回、短い電話をかける AI の見守りサービス**である。雑談の中で体調と食事を聞き取り、3 つのルールで異変を検知し、職員のトリアージキューと家族のダッシュボードに出す。

開発期間は 2026-10-02 から 10-06 の 5 日間、コミット数 31。

### 1.1 サービス構成

| サービス | 役割 | リージョン |
|---|---|---|
| `telephony` | Twilio との発信・着信、通話のブリッジ（緊急時の三者通話）、配信結果の受け取り | us-central1 |
| `voice-gateway` | Gemini Live との双方向音声中継。**通話中**の R1 検知と緊急対応 | us-central1 |
| `analyzer` | 通話後の解析。要約、記憶、標準化質問の回答、R2・R3 の判定 | asia-northeast1 |
| `notifier` | SMS・メール・プッシュ・音声通報の送信と配信結果の記録 | asia-northeast1 |
| `api` | 職員・家族向けの REST API。Firebase Auth で認可 | asia-northeast1 |
| `web` | React 19 + Vite の画面。Firebase Hosting | （CDN） |

共有部分は `packages/core`（検知ルール・優先順位・通知方針・標準化質問）、`packages/store`（Firestore とインメモリの両実装）、`packages/cloud`（Cloud Tasks・OIDC）。

## 2. 画面一覧

本番 URL は <https://hachicall-nao.web.app>。全 9 ページ・13 ルート（うち 4 つは転送用）。

認証は Firebase Auth で、**職員はカスタムクレーム `role: staff`、家族は確認済みのメールアドレス**で見分ける。サインインしていない人は家族ログインに送られる。職員・家族ともサインインの方法は Google・パスワード・メールリンクの 3 通りある。

### 2.1 ログインと認証（3 ページ）

| 画面 | ルート | 内容 |
|---|---|---|
| 職員サインイン | `/staff/login` | 「Staff sign in」。パスワード再設定も自分でできる。失敗した本当の理由を表示する |
| 家族サインイン | `/family/login` | 「Family sign in」。職員が登録したメールアドレスを使う。相互にリンクしており、誤って逆の画面に入っても案内が出る |
| メール確認の完了 | `/family/finish` | メールリンクから戻ってきたときの着地点。リンクが無効な場合は「This link does not work」を表示 |

認可は `Guard` コンポーネントで行い、役割が違う場合は「この画面は介護チーム用です」と**理由を明示して**止める。黙ってリダイレクトしない。

### 2.2 職員向け（4 ページ）

| 画面 | ルート | 内容 |
|---|---|---|
| トリアージキュー | `/staff` | 「Needs attention」。検知したケースを緊急度と優先順位で並べる。**本人が電話を希望した依頼**（承認待ち）もここに出る |
| ケース詳細 | `/staff/cases/:id` | 利用者名・緊急度・ルール、「What was said」（文字起こしと該当箇所から再生できる録音プレイヤー）、「Speech over time」（話し方の推移と本人の平常範囲）、標準化質問の集計、送信した通知、ケースの更新履歴 |
| 利用者一覧 | `/staff/residents` | 「Residents」。登録済みの利用者、通話時刻、連絡先、**気分を家族に共有する同意**のチェックボックス |
| 利用者の登録 | `/staff/residents/new` | 「Add a resident」。本人・家族・担当職員の連絡先、通話時刻、タイムゾーン |

### 2.3 家族向け（2 ページ）

| 画面 | ルート | 内容 |
|---|---|---|
| 見守り対象の選択 | `/family` | 「Who would you like to check on?」。複数の利用者に紐付いている場合に選ぶ。紐付きがない場合はその旨を表示 |
| ダッシュボード | `/family/residents/:id` | 「Daily calls with …」。直近 2 週間の様子（体調・気分・食事・社会的つながりのタイル）、よく出る話題、通話ごとのやさしい要約、送られたアラートの一覧と配信状況、介護チームの連絡先、この端末のプッシュ通知設定 |

家族の画面には**引用・話し方の分析・点数・尺度名を出さない**（FAM-03）。本人の気分や孤独感は、職員が本人から聞き取った同意が記録されている場合にのみ表示・送信する。

### 2.4 画面に関する設計上の判断

- **職員画面は横幅を使い切る。** キューと利用者一覧はタイル表示、ケース詳細は「根拠」と「記録」の 2 列に分けた
- **矢印（傾向）は過去 3 通話未満では出さない。** データが足りないのに傾向を示すのは嘘になる
- **家族向けの見出しは、本人が言ったか・したことからだけ書く。** 裏付けとなるタグが残らなかった気分は見出しから落とし、タイルと矛盾しないようにした
- **デプロイ後に古いアプリを配り続けない**ようにキャッシュを設定した

### 3.3 テストが何を守っているか

数を並べるより、何のためのテストかを書いておく。

- **R1 の境界。** `packages/core/test/r1.test.ts` の 150 件はほぼ**除外**のためにある。「火曜まで医者に会えない（can't see the doctor until Tuesday）」「なぜそう言うのか分からない（can't see why）」「眼鏡をなくした」「昨夜ひどい頭痛だったが治った」「友人が入院した」はいずれも R1 ではない
- **推測された回答は無回答より悪い。** 標準化質問の回答は、本人以外の発話に紐付いたもの、語彙にない質問 ID、その質問が提示していない選択肢をすべて破棄する
- **電話番号は本人の発話から読み直す。** モデルの出力は宛先にしない。倍数語（double / triple）や 1 発話に 2 つの番号があれば採用しない
- **同意がなければ家族に何も送らない。** 孤独感の通知はテストで同意ゲートを強制している
- **データ層は 2 実装で同じ契約を満たす。** インメモリと Firestore を同じ契約テストにかける
- **家族向けの文面に点数・尺度名・診断語を入れない。** テストで禁止している

## 4. 検知精度の評価（合成データ）

自動テストは「書いたとおりに動くか」しか見ない。検知の精度は別に測った。**レポートに出てくる人物・通話・音声はすべて合成**で、実際の利用者のデータは使っていない（USR-04）。

### 4.1 R1 / R2 — 本番の解析 Worker を通した 528 通話

全文: [eval/r12-synthetic.md](eval/r12-synthetic.md)

49 ケース × 2 通りの言い回し × 2 シード × Gemini 2 サンプル = **392 件の判定**。R2 のケースは過去の通話を伴うため、解析した通話は延べ **528 通話**になる。モデル `gemini-3.8-flash`、実行 643 秒。本番と同じ `analyzeCall()` をインメモリのストアに対して流し、Firestore にも Cloud Storage にも書かず、電話も SMS も出さない。

| 指標 | 結果 |
|---|---|
| R1 感度（危険を緊急として拾えたか） | 128/128（100%） |
| R1 特異度（危険でないものを拾わなかったか） | 264/264（100%） |
| R1 ハードネガティブ（慣用句・他人・過去・冗談・仮定） | 128/128（100%） |
| R1 キーワードルール単独 | 感度 100% / 特異度 100% |
| R1 Gemini 単独 | 感度 100% / 特異度 100% |
| R2 感度（2 日以上の欠食を「至急」まで上げたか） | 60/64（94%） |
| R2 特異度 | 321/328（98%） |
| Gemini のエラー（再試行後） | 0 |

**この数字は作り直した後のもので、最初はもっと悪かった。** 初回は R1 特異度 85%（40 件の誤検知はすべてキーワードルール由来、Gemini 単独では 0 件）、ルール単独の感度は 56% だった。そこで `detectR1` を文単位の一般規則に作り直した（誰の症状か、慣用句、過ぎ去った症状、持病による長年の制限）。**ルールと Gemini を併用しているのは、通話中はルールしか使えないから**である。Gemini の判定は通話後にしか得られず、通話中に救急へつなぐ判断には間に合わない。

**R2 の外れ方は 2 ケースに集中している**（外れた run はそのケースの言い回しとサンプルの繰り返しなので、実質 2 種類の失敗である）。

- **検知漏れ**（4 run / 1 ケース）: 「ここ数日ほとんど食べていない」と 1 回の通話でまとめて報告されたケース。過去の通話記録がないため日数を積み上げられず、「至急」に届かず「要注意」になった
- **誤検知**（7 run / 1 ケース・2 通りの言い回し）: 血液検査前の絶食。「後でちゃんと昼を食べる」と言っているのに、前日が風邪で食欲不振だったため 2 日連続の不良と誤って数えた

どちらも**日数の数え方**の問題で、文意の読み取りではない。1 回の通話で報告された複数日を数えられないこと、予定された絶食を不良と区別できないことが原因である。

### 4.2 R3 — 合成録音 150 通話

全文: [eval/r3-synthetic.md](eval/r3-synthetic.md)（別シードの結果は [eval/seed-7/](eval/seed-7/)）

10 人 × 15 通話。Cloud Text-to-Speech で、間と言い直しを台本で制御した音声を生成し、本番と同じ測定経路（VAD による応答潜時 + Gemini の聴取 + ベースライン比較）に流す。

| 指標 | 結果 |
|---|---|
| 変化した人の検知（感度） | 5/5（100%） |
| 安定した人の誤検知 | 0/5 |
| 評価対象となった安定通話あたりの誤検知 | 0/14（0%） |
| 最初の検知までの平均遅れ | 変化開始から 2.0 日 |
| 応答潜時の測定誤差 | 平均絶対誤差 10 ms、最大 37 ms（150 通話） |
| 言い直しの聴取 | 再現率 97% / 適合率 97% |
| 台本と測定値の相関（言い直し/100語） | Pearson r = 0.99 |

**除外が働いていることも確認できた。** 風邪の日の通話（syn-s4、30 日目）は一時的要因として除外され、仮に使っても警告は出なかった（SPK-04）。緊急度が期待とずれたのは 1 人（軽度の複合変化を「要観察」ではなく「要対応」と判定）で、安全側の外れ方である。

### 4.3 この評価で言えないこと

正直に書いておく。

- **合成データである。** 手書きの英語の文字起こしと、きれいな回線の TTS 音声。実際の発話はもっと雑で、音声認識の誤り・訛り・かぶりは再現していない
- **開発セットでの数字である。** R1 のルールは初回の結果を見て作り直したので、新しい言い回しに対する性能を過大評価している。偏りのない推定には、見ていない発話での試験が必要
- **標本が小さい。** 約 50 ケース・10 人なので信頼区間は広く、1 ケースで数ポイント動く。わざと難しいケースを選んでおり、実際の出現頻度を反映した数字ではない
- **ラベルは 1 人の判断である。** 救急車が去った直後、運動後の息切れなどの境界例は、別の判断もありえる
- **通話中の除外には限界がある。** Gateway は届いた断片ごとに判定するので、症状の**後**に来る言葉（「…でも大丈夫でした」）に依存する除外は、同じ断片に入っていなければ働かず、警告を出す

## 5. 実機での試験（本番環境 `hachicall-nao`）

Twilio のトライアルアカウントで行い、発信先と家族役は Verified Caller IDs に登録した日本の携帯電話。試験用の利用者は毎回新しく作る。

### 5.1 2026-10-02 の試験

**発信 — 成功**

Cloud Scheduler → Cloud Tasks → 発信 API → Twilio → 携帯に着信 → ステータス通知 → Firestore。通話状態 `completed`、通話時間 12 秒を記録。

判明したこと: Twilio の API キーは Standard 種別が必要（Restricted で権限がないと 401 / エラー 8001）。

**通話中の急変検知（R1）— 一部失敗、修正済み**

台本の発話「I ate mochi and it's in my mouth. I can't breathe.」に対して:

| 項目 | 結果 |
|---|---|
| R1 の検知 | 成功。通話中に検知し、緊急ケースを作成 |
| 家族への呼び出し電話 | **成功**。家族役の携帯に着信 |
| 本人への案内と通話の扱い | 成功。終了理由 `emergency`、通話 82 秒・10 往復、録音を保存 |
| 家族への SMS | **失敗**。検知から 4 秒で送信し「送信済み」と記録したが、Twilio の配信状態は `undelivered`（エラー 30003）で携帯には届かなかった |

原因は、家族向け SMS の本文に担当職員の電話番号が入っていたこと。Twilio の日本向けガイドラインでは本文への電話番号の記載が禁止されており、携帯会社で止められたと考えられる（SMS は 2 セグメントの長文だった）。家族向け SMS から電話番号の行を外し、メールと音声通報には残し、職員の連絡先はダッシュボードで表示するようにした（FAM-04）。**この修正の着信確認は §5.4 で完了している。**

**通話後の解析（R2）— 成功**

台本の発話「I haven't really eaten for two days. I have no appetite.」に対して、食事の記録「不十分・2 日間」、R2 ケースを「至急」で作成、次回の通話用の記憶（孫の訪問予定・園芸）を保存。話し方（R3）は発話量が足りず評価対象外（設計どおり）。

判明したこと: デプロイ済みの Voice Gateway が古いイメージのままで、通話終了後の解析依頼が出ていなかった（環境変数だけを追加していた）。このとき**解析 Worker の 10 分ごとのスイープが代わりに拾って解析した**ので、依頼が失われても解析されることを本番で確認できた。

### 5.2 その後に解消したこと

### 5.4 親族・職員への SMS 再試験（2026-10-06）— 成功

10-02 の唯一の失敗だった SMS の着信を、実機で確認した。

**結果：本文が文言だけであれば届く。URL を入れると届かない。**

10-02 の失敗原因は本文に担当職員の電話番号が入っていたことだったが、同じ規制は URL にも及ぶことが分かった。海外の送信元からの SMS について、日本の携帯会社は**リンクと電話番号のどちらを含んでも黙って破棄する**。送信側には成功として返るため、配信結果を記録していなければ失敗に気付けない。

これは設計どおりの挙動で、該当箇所には以前から同じ判断が書かれている。

`packages/core/src/notifications.ts`（89〜93 行）:

```ts
/**
 * Japanese carriers silently drop SMS from overseas senders that contain a link or a phone number,
 * and long messages are split into parts that may not be reassembled. SMS therefore carries no
 * link or number and fits in one part: 160 plain characters, or 70 when it needs Unicode (Japanese).
 */
```

そのため SMS の文面は `fitSms()` を通し、リンクも番号も載せず、1 セグメント（半角 160 文字・日本語を含む場合 70 文字）に収めている。行き先は URL ではなく画面の名前で示す（「詳細は職員画面で」「Open the Hachi staff queue for details.」）。**URL はメール・プッシュ通知の側に残してある**ので、情報そのものが失われるわけではない。チャネルごとに本文を分けている理由がこれである。

自動テストでも固定している（`packages/core/test/notifications.test.ts`）。

| 守っている内容 | 判定方法 |
|---|---|
| SMS にリンクを含めない | `expect(m.body).not.toMatch(/https?:\|www\./)` |
| 1 セグメントに収める | 半角のみ 160 文字以下、Unicode を含む場合 70 文字以下 |
| メールには URL を残す | `expect(email.body).toContain('Case: https://…')` |

残る制約は、**配信可否が携帯会社側の判断であり、こちらでは検証できない**点である。だから送って終わりにせず、Twilio のステータス通知を受けて実際の配信状況を画面に出している。

## 6. 判断基準の裏付け

「いつもと違う」の基準は、自分で考えた質問ではなく**公表された尺度**に紐付けた。詳細は [CLINICAL_BASIS.md](CLINICAL_BASIS.md)。

| 尺度 | 用途 | カットオフ |
|---|---|---|
| ULS-3（UCLA 孤独感尺度 短縮版） | 孤独感 | 6 以上 |
| PHQ-2 | うつ | 3 以上（感度 83%・特異度 92%） |
| CDC STEADI | 転倒リスク | key questions 3 問のうち 1 問でも該当 |
| FRAIL scale | フレイル | **結果を出さない**（5 項目のうち 2 項目が電話で尋ねられないため） |
| 基本チェックリスト（厚生労働省） | 7 領域への対応づけ | 領域別の公式基準 |

**Hachi は基本チェックリストを実施しない。** 公式の文言は変更も翻訳もできず、利用者は英語話者だからである。英語で検証された尺度で尋ね、結果を 7 領域に対応づけて「回答済み項目数／全項目数」とともに報告する。点数は出さない。回答が足りない領域は「判定不能」とし、電話で測れない項目（項目 12 の BMI）は欠測として明示する。

報告は**2 つの枠で出す**。日本のケアマネージャーには 7 領域が必要で、本人・家族・英語圏の医師には尺度それ自体の結果が読める。どちらか一方からもう一方は導けない。
