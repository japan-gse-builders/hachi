## 0. 方針

| 項目 | 方針 |
|---|---|
| 言語 | TypeScript（Node.js 22）でバックエンド・Web UIを統一。型とドメインロジックを `packages/core` で共有する |
| Google サービス | Cloud Run / Cloud Scheduler / Cloud Tasks / Cloud Storage / Firestore / Gemini Live API（Vertex AI）/ Gemini（通話後分析）/ Firebase Authentication / Firebase Hosting / Firebase Cloud Messaging（FCM）/ Secret Manager / Cloud Monitoring・Logging / Cloud Build / Artifact Registry |
| Google 以外 | 電話網（PSTN）と WhatsApp 通話への発信は Google に代替サービスがないため Twilio を使う（図の「Twilio候補」）。SMS も Twilio、メールは SendGrid などを Twilio 経由で使う |
| リージョン | `asia-northeast1`（東京）を基本とする。Gemini Live API の提供リージョンは実装前に確認し、未提供なら最寄りのリージョンを使い、遅延を計測する |
| テスト | Vitest。ドメインロジックは単体テストでカバレッジ90%以上、Firestore は Firebase Emulator を使った結合テスト、電話と Gemini はモックした E2E テスト。CI でテストが1件でも失敗したらマージ不可とする |

### リポジトリ構成

```
packages/core          ドメインロジック（検知ルール・優先順位付け・ケース統合・通知ポリシー・スケジュール）※純粋関数のみ
packages/infra         Firestore / Cloud Tasks / GCS / Secret Manager のアダプタ
services/api           Cloud Run: API（職員・親族向けの REST API、発信処理 API）
services/dispatcher    Cloud Run: 発信ディスパッチャ（Scheduler から起動）
services/voice-gateway Cloud Run: Voice Gateway（Twilio Media Streams ⇄ Gemini Live、通話中の R1 監視）
services/analysis      Cloud Run: Analysis Worker（通話後分析）
services/notifier      Cloud Run: 通知 Worker（SMS / メール / FCM プッシュ / 音声通報）
apps/web               Firebase Hosting: Web UI（職員用トリアージキュー＋親族用ダッシュボード、PWA）
```

## 1. 全体の流れ（architecture.png に対応）

1. **発信**: Cloud Scheduler（毎分）→ 発信ディスパッチャが「今から発信すべき利用者」を Firestore から抽出 → 利用者ごとに Cloud Tasks に発信タスクを登録（タスク名 = `利用者ID + 現地日付` にして二重発信を防ぐ）→ 発信 API が Twilio に発信を依頼する。
2. **通話**: Twilio が利用者の携帯電話（通常の電話 または WhatsApp）に発信し、通話がつながると WebSocket で Voice Gateway に音声を流す。Voice Gateway は音声を変換（μ-law 8kHz ⇄ PCM 16kHz / 24kHz）して Gemini Live API と双方向に中継する。
3. **通話中の R1 監視**: Voice Gateway は ①Gemini の関数呼び出し（`report_emergency`）と ②文字起こしに対するルールベースの検知（`packages/core` の R1 モニタ）の2系統で R1 を監視する。どちらかが反応すれば「緊急」とし（PRI-04）、ケース更新・通知 Outbox に書き込む。通話は切らずに、緊急通報を促す案内に切り替える（CNV-05）。
4. **保存**: 音声と時刻情報を Cloud Storage へ、文字起こしと通話のメタデータを Firestore へ保存する（CNV-06）。
5. **通話後分析**: 通話終了で Cloud Tasks に分析タスクを登録 → Analysis Worker が Gemini で R1/R2 の判定、話題の記録（CNV-07）、話し方の特徴量（SPK-01）を算出 → `packages/core` でケースを統合・緊急度判定・順位付け → ケース更新と通知 Outbox を Firestore のトランザクションで書き込む。
6. **通知**: Outbox → Cloud Tasks → 通知 Worker → SMS / メール / FCM プッシュ /（緊急のみ）親族への自動音声電話。
7. **閲覧**: Firebase Authentication でログイン → Firebase Hosting の Web UI → Cloud Run API → Firestore / Cloud Storage（音声は署名付き URL で再生）。

### フェーズ 0: 基盤（0.5日）
- npm workspaces のモノレポ、TypeScript、Vitest、ESLint、Prettier
- GitHub Actions（または Cloud Build）で lint・型チェック・テストを実行
- `.env.example` と Secret Manager の利用方針（認証情報はコードに書かない）

### フェーズ 1: ドメインコア `packages/core`（2日）★最初に実装
クラウドに依存しない純粋関数として実装し、網羅的にテストする。
- 緊急度の定義と比較（2章）
- R1 モニタ: 英語の発話から差し迫った危険の訴えを検知。否定・過去・他人の出来事を除外し、遠回し・控えめな表現は拾う（DET-02, DET-05）
- R2 評価: 食べられていない日数を前回までの通話と合わせて数え、1日なら経過観察、2日以上なら至急（DET-04）
- R3 特徴量: 語彙の多様さ（MATTR）、言い直し率、応答までの時間、話題の一貫性（Gemini の採点を受け取る）（SPK-01）
- R3 ベースライン: 4週間・最低通話数を満たした場合にベースラインを作り、変化の大きさ・傾向・寄与した特徴を算出。解析に適さない通話は除く（SPK-02〜04）
- ケース統合: 同じ利用者・同じルールは1ケースにまとめ、緊急度を上げる方向にのみ自動更新（PRI-01, PRI-04, PRI-05）
- 優先順位付けと理由文（PRI-02, PRI-03）
- 通知ポリシーと通知文面（NTF-01〜03）。文面に文字起こしや話し方の解析結果を含めない（FAM-03）
- 発信スケジュール: 利用者のタイムゾーンで次回の発信時刻を計算（夏時間対応）

### フェーズ 2: データ層と API（2日）
- Firestore のデータモデル（下記）とリポジトリ層、Firebase Emulator による結合テスト
- Firebase Authentication: 職員はメール+パスワード、親族は SMS またはメールのワンタイム認証（FAM-01）。カスタムクレーム `role=staff|family` と `residentIds` で閲覧範囲を制限
- API: 利用者の登録（USR-01〜03）、過去の通話記録の取り込み（USR-04）、キュー一覧・ケース詳細・状態更新（QUE-01〜03）、職員による修正履歴の蓄積（PRI-06）、親族ダッシュボード（FAM-02〜04）
- Firestore セキュリティルール（クライアントから直接は書き込ませない）とそのテスト

### フェーズ 3: 発信パイプライン（1.5日）
- 発信ディスパッチャ、Cloud Tasks（冪等なタスク名）、発信 API
- Twilio の発信（通常の電話／WhatsApp）、ステータスコールバック、Webhook の署名検証
- 技術的な失敗（Twilio のエラー、Gateway の障害）は自動で再発信。「出ない（不応答）」の再発信は MVP の範囲外
- 実装済みの二重発信対策: タスク名と通話 ID を「利用者・現地日付・試行回数」から決める。通話記録は一度だけ作成し、短時間の発信権（リース）を持つワーカーだけが発信する。Twilio の一時的なエラーは Cloud Tasks の再配信で 3 回まで再送し、それでも失敗したら 3 分後に次の試行（最大 3 回）を予約する。番号未認証などの恒久的なエラーは再発信しない
- 発信レートは Cloud Tasks のキューで毎秒 1 件に制限（Twilio の初期上限）

### フェーズ 4: Voice Gateway（4日）★最重要・最難関
- Twilio Media Streams ⇄ Gemini Live API の双方向中継、音声フォーマット変換
- システムプロンプト: 名乗りと AI であることの告知（CNV-02）、雑談の進め方（CNV-03, 09〜12）、前回の話題の引き継ぎ（CNV-07, 08。記録にない事柄は話さない）
- 沈黙を遮らない設定（Gemini の音声区間検出の感度と無音の許容時間を調整）（CNV-04）
- 通話中の R1 監視（2系統）→ 緊急の案内・通知（CNV-05, NTF-01）、親族または職員への転送（下記「追加提案1」）
- 通話時間の管理（3〜5分を目安に自然に終える）
- Gemini の接続が切れた場合のセッション再開、失敗時の定型音声での案内と終了

実装の要点:
- Gateway は Gemini Live（`gemini-3.8-live`、東京リージョンでは未提供）に近い us-central1 の Cloud Run で動かす。CPU 常時割り当て、最小 1 インスタンス。音声は米国で処理される（データ所在地の注意点）
- Twilio の操作（会話後の振り分け、電話会議、親族・職員への呼び出し）はすべて発信サービスが担う。Gateway は会話の終了理由を Firestore に書いてからストリームを閉じ、Twilio が `/twilio/after-stream` に問い合わせる
- ストリームの認証: 発信時に通話ごとのトークンを作って Firestore に保存し、TwiML のパラメータで渡す。Gateway は一致しなければ即切断する
- 緊急時: 正規表現の R1 モニタと Gemini の `report_emergency` ツールのどちらかが反応したら、R1 ケースを作り、SMS・メールを Outbox に予約し（音声通知は転送で代替）、専用キュー `emergency-calls` で発信サービスに転送を依頼する。利用者には連絡中であることと 119 番を案内し、電話会議に移す。親族・職員には「1 を押すとつながる」電話をかける（同意なしで実施し、利用者に告げる方針）
- 障害時: Gemini は 3 回まで接続を再試行し、通話中に切れたら会話の続きから再開（同じストリームで最大 3 セッション）。Gateway 自体が落ちた場合は Twilio が発信サービスに戻り、最大 3 回までストリームを張り直す。それでも駄目なら定型の謝罪を流して再発信を予約する
- 通話時間: 既定 8 分。終了 45 秒前に締めくくりを促し、上限で切る。緊急対応中は自動で切らない
- 録音: 2 チャンネル（左 = 利用者、右 = Hachi）の WAV を Cloud Storage に保存。割り込みで再生されなかった音声は除く
- Twilio の試用アカウントでは、親族・職員の番号も認証済み発信者番号に登録しないと緊急転送の試験ができない

### フェーズ 5: 通知（1.5日）
- Outbox パターン（ケース更新と通知予約を同一トランザクションで書き込み、送信漏れを防ぐ）
- 通知 Worker: SMS / メール / FCM Web プッシュ /（緊急のみ）親族への自動音声電話を並行送信。送信日時と送信先をケースに記録（NTF-04）
- 冪等キーで二重送信を防止、Cloud Tasks の再試行と送信失敗時のデッドレターキュー

実装の要点:
- 通知 Worker は asia-northeast1 の非公開 Cloud Run（呼び出せるのは Cloud Tasks / Scheduler のサービスアカウントだけ）。アプリ側でも OIDC トークンを検証する
- 送信の流れ: ケース更新時に Outbox（Firestore `outbox`）へ書き込み → 送信タスクをキュー `notifications` に投入 → Worker が 1 件ずつ送信。緊急時は Gateway が転送依頼の直後に投入する。投入に失敗しても、毎分のスイープが 2 分以上動きのない未送信分を拾う
- 二重送信の防止: 送信済み・失敗・スキップの通知は二度と送らない。送信中は 60 秒の排他（リース）を取り、同じ通知の重複タスクは待たせる。送信成功の直後に書き込みが失敗した場合のみ、再送の可能性が残る（少なくとも 1 回は届くことを優先）
- 再試行: 一時的なエラー（5xx、429、ネットワーク、認証設定の誤り）は Cloud Tasks のバックオフで最大 8 回。恒久的なエラー（番号の誤りなど）は即座に「失敗」として残し、Error ログを出す（Firestore の `failed` がデッドレターの代わり）
- チャネル: SMS は Twilio（送信元 `+19787559139`、宛先は `SMS_ALLOWED_PREFIXES` で +81 のみに制限）、音声通報は Twilio の発信（URL を除いた文面を 2 回読み上げ）、プッシュは FCM、メールは SendGrid。SendGrid の鍵が未設定ならメールは「スキップ」として記録する
- NTF-04: 送信に成功したら、送信日時・チャネル・送信先をケースの `notifications` に記録する（重複して記録しない）
- ログには宛先（個人情報）を出さず、Outbox の ID だけを出す

### フェーズ 6: Analysis Worker（2.5日）
- Gemini（構造化出力・JSON スキーマ指定）で、R1/R2 の判定、根拠となる発話と音声の該当箇所、話題・予定・好きなことの抽出、話題の一貫性の採点
- 体調・食事の要約（会話にない事柄を書かない。要約に使った発話への参照を必須にして検証する）（QUE-02, FAM-03）
- 話し方の特徴量の算出とベースラインとの比較 → ケース統合・優先順位付け → 通知

実装の要点:
- 解析 Worker は asia-northeast1 の非公開 Cloud Run（呼び出せるのは Cloud Tasks / Scheduler のサービスアカウントだけ）。アプリ側でも OIDC トークンを検証する。モデルは `gemini-3.8-flash`（`GEMINI_LOCATION` 既定 `global`）。職員向け要約の言語は `STAFF_LOCALE`（既定 `en`）、親族向け要約は常に英語
- 流れ: 通話が終わると Gateway が 1 分後の解析タスクをキュー `call-analysis` に積む（キーはストリームごとなので、途中で切れて再開した通話も改めて解析する）。投入に失敗しても、10 分ごとのスイープが、終了から 5 分以上経った未解析の通話を拾う
- 排他: 解析中は 5 分のリースを取る。二重のタスクは 503 で待たせる。文字起こしを保存できなかった通話は積まない
- モデルの出力はスキーマで受け取り、もう一度検証する。R1 の引用は、指し示した利用者の発話に実際に含まれていなければ、その発話そのものを根拠にする。通話中の正規表現モニタ（`detectR1`）も後から走らせ、モデルが見逃した急変を拾う。通話中に緊急対応済みの通話は、R1 を重ねて出さない
- R2 は直近 7 日の食事記録と合わせて日数を数える。R3 は本人のベースラインとの比較だけで、他の人とは比べない。取り込み済みの過去の通話は要約と特徴量だけを残し、通知は出さない
- モデルが使えないとき: 一時的な失敗（429、5xx、ネットワーク、不正な出力）は Cloud Tasks が再試行し、4 回目で規則ベースの確認だけを残して完了する。恒久的な失敗（400）は最初から規則ベースに切り替える。要約が書けなくても R1 の見逃しは残さない
- 検知が出たら既存の `recordDetections` でケースと Outbox を書き、通知 Worker へ即時投入する（失敗しても通知側のスイープが送る）。同じ通話の根拠が開いているケースに既にあれば重ねない
- 次の通話: 直近の解析から話題・予定・好きなことを最大 10 件、プロンプトに渡す。直前の食事が不十分なら、その日の食事を丁寧に聞く（CNV-07, CNV-08, DET-04）
- ログには文字起こしを出さず、利用者 ID・通話 ID・結果だけを出す

### フェーズ 7: Web UI（3日）
- React + Vite、PWA 対応、スマートフォン優先のレスポンシブデザイン、大きな文字とボタン、専門用語を避けた表示
- 職員: トリアージキュー（緊急は最上位で赤く表示、リアルタイム更新）、ケース詳細（文字起こし・音声の該当箇所の再生・話し方の推移グラフ）、状態と緊急度の修正
- 親族: 直近2週間の通話一覧、通話ごとの平易な要約、次回の電話の予定、通知の履歴と対応状況、担当職員の連絡先。ホーム画面への追加とプッシュ通知の許可を案内

### フェーズ 8: 信頼性・総合テスト・デプロイ（2日）

## 4. 性能と信頼性（「電話を失敗させない」ための設計）

| リスク | 対策 |
|---|---|
| 通話開始時の待ち時間（コールドスタート） | Voice Gateway と発信 API は最小インスタンス数を1以上、CPU を常時割り当て。通話がつながる前に Gemini Live のセッションを確立しておく |
| 応答の遅さ | 20ms 単位の音声フレームでそのまま中継、変換処理はメモリ上で完結。東京リージョンと Twilio の東京エッジを使用。発話終了から AI が話し始めるまで 1 秒以内を目標に計測 |
| 長時間の WebSocket 接続 | Cloud Run のタイムアウトを 15 分に、1インスタンスあたりの同時接続数を制限（例: 20）、セッションアフィニティを有効化 |
| Gemini Live の切断 | セッション再開で継続、再開できなければ定型の案内をして終了し、技術的な失敗として再発信 |
| Twilio・Cloud Tasks の一時的な障害 | 指数バックオフで再試行、冪等なタスク名で二重発信を防止 |
| 緊急通知の遅延・送信漏れ | 通話中に検知したら Outbox を即時に書き込み、Cloud Tasks を経由せず直接送信も試みる（どちらか早い方。冪等キーで重複を防ぐ）。検知から1分以内の送信を監視 |
| 障害に気付かない | 通話の成功率、通話開始までの時間、緊急通知の所要時間をメトリクス化し、しきい値を超えたら運用担当に通知 |

## 5. 要件にない・不足していると考える点（MVP として最小限の提案）

重要度順。★ は MVP に含めることを推奨するもの。

1. ★**通話の転送（ご説明の「懸念があれば電話をつなぐ」）**: 要件 CNV-05 は「緊急通報を促す」だけで、転送には触れていない。→ 6章の決定により、緊急時は同意を待たずに親族と担当職員の両方へ同時に電話をかけ、最初に出た人を本人との通話につなぐ。AI が自動で緊急通報番号（119 / 911 など）にかけることは法令・運用上の問題があるため行わず、本人に通報を促す。
2. ★**WhatsApp などのネット通話**: Twilio の WhatsApp Business Calling を使う。企業側からの発信には本人の事前の許可が必要で、提供状況と条件は実装前に検証が必要。利用者ごとにチャネルを設定し、WhatsApp で失敗した場合（技術的な失敗）は通常の電話にかけ直す。LINE などの他のアプリは企業からの通話 API がないため対象外とする。
3. ★**親族への緊急通知の確実性**: 要件では受信確認と再通知は範囲外だが、命に関わるため、緊急時は SMS・メール・FCM プッシュ・**自動音声電話**を同時に送ることを提案する（どれか1つが届けばよい）。iPhone ではホーム画面に追加しないと Web プッシュが届かないため、プッシュだけには頼らない。
4. ★**技術的な失敗による再発信**: 「出ない」とは別に、システム側の障害で通話できなかった場合は自動でかけ直す（要件の「不応答の再発信」とは区別）。
5. ★**通話途中で切れた場合の緊急処理**: R1 の訴えの直後に通話が切れても、通知は必ず送る。
6. ★**セキュリティと個人情報**: Twilio Webhook の署名検証、認証情報は Secret Manager に保存、サービスごとに最小権限のサービスアカウント、Firestore と Cloud Storage へのクライアントからの直接アクセス禁止、音声は短時間だけ有効な署名付き URL で再生、操作ログの記録、データの保存期間の決定。
7. ★**AI の安全上の制約**: 医療的な助言や診断名を口にしない、緊急時に「様子を見ましょう」などと言わない、記録にない事柄を覚えているように話さない、をプロンプトとテストで担保する。
8. **録音の告知**: 冒頭で AI であることに加えて録音していることも伝える（国・地域の法令による）。
9. **言語**: 要件は英語だが、日本の利用者を想定するなら日本語への切り替えが必要。R1 モニタと文面は言語ごとに差し替えられる設計にする。
10. **費用の上限**: Gemini と Twilio の利用料の予算アラート、通話時間の上限（例: 8分で自動終了）。
