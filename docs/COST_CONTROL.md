# AI 支出の上限

毎日、利用者一人につき一通話。Live セッションも通話後の解析もトークン課金で、どちらも利用者数に比例して毎日積み上がる。止める仕組みがなければ、設定ミスや応答のない通話が続いた月の請求は誰かが気づくまで伸び続ける。

防御は二重にしてある。**一次はアプリ側**（この文書の本体）、**二次は Google Cloud の請求側**（§6）。アプリ側が壊れても請求側が残り、請求側はアプリの挙動を変えられないので、両方いる。

ただし**順序が逆だと二重防御ではなく二重の事故になる**。2026-10-08 に起きたのはそれで、§2 と §3 はその後始末である。

## 1. 何を数えているか

単位は**マイクロドル（100 万分の 1 ドル）の整数**。浮動小数点の金額は、よりによって「発信してよいか」を決める比較のところで誤差が出るので使わない。

| 対象              | 計上           | 既定の単価                               |
| --------------- | ------------ | ----------------------------------- |
| Gemini Live（通話） | 通話秒数 × 分単価   | `GEMINI_LIVE_PRICE_PER_MIN` = $0.15 |
| 通話後の解析（入力）      | トークン数 × 百万単価 | `GEMINI_PRICE_IN_PER_M` = $1.5      |
| 通話後の解析（出力）      | トークン数 × 百万単価 | `GEMINI_PRICE_OUT_PER_M` = $7.5     |

単価は 3 サービス（telephony / analyzer / api）が同じ台帳に書くので、パースは `packages/core/src/spend.ts` の `parseSpendSettings()` 一箇所にある。サービスごとに違う単価を読んでしまうと、その月の合計が何の数字でもなくなる。

### 単価は「請求額」ではなく「定価」

ここに入れる数字は、**我々が払う額ではなく Vertex AI の定価（list price）**である。理由は §3 にある。出典（2026-10-08 時点、[Agent Platform の生成 AI 料金ページ](https://cloud.google.com/gemini-enterprise-agent-platform/generative-ai/pricing)）：

| モデル | 項目 | 定価 / 1M tokens |
| --- | --- | --- |
| `gemini-3.8-flash`（global） | 入力（text / image / video / audio） | **$1.50** |
| | テキスト出力（応答 + 推論） | **$7.50** |
| `gemini-3.8-live`（non-global） | 音声入力 | **$3.00** |
| | 音声出力 | **$12.00** |
| | テキスト入力 | $0.75 |
| | テキスト出力（応答 + 推論） | $4.50 |

- **Flash の `$0.75 / $3.75` は定価ではない。** 2026-12-31 までの導入価格で、ページの脚注どおり「50% credits back on net spend」——つまり **$1.50 / $7.50 に対するクレジット**として与えられる。2027-01-01 からは定価そのものが請求される。どちらにしても我々が入れるべき数字は $1.50 / $7.50 ひとつで足りる。
- **Live は導入割引がない**ので、定価 = 請求額。`us-central1` を使っているので non-global の行が該当する（`GEMINI_LOCATION` の既定値、`services/voice-gateway/src/config.ts`）。解析側の Flash は `global` なので global の行。
- **AI Studio の料金ページ（`generativelanguage.googleapis.com`）とは別物。** Hachi は `GoogleGenAI({ enterprise: true, ... })` で Vertex AI を呼んでいる。無料トライアルのクレジットが効くのも Vertex AI 側だけで、AI Studio には効かない。

### Live の分単価はどこから来たか

Vertex は Live を**分ではなくトークンで**課金する。音声は **1 秒あたり 25 トークン**（料金ページの換算値）なので 1 分 = 1,500 トークン、両方向を全時間数えても $3 + $12 で **$0.0225/分**にしかならない。それでも分単価を持っているのは、`callReservationMicros()` が**電話が鳴る前に**答えを出さなければならず、その時点で分かっているのは `MAX_CONVERSATION_SEC` だけだからである。

問題は、Live が**毎ターン、セッションコンテキスト全体を再課金する**ことにある（料金ページ "Live API Billing Details"）。過去のターンの音声トークンは、以後のターンごとに音声入力レートで何度も請求される。つまり 1 通話のコストは**長さの二乗に比例して**伸びる。既定 480 秒（8 分）で 10 月の実測と同じ約 15 秒のターンなら再課金は約 16 回、**$0.09/分**相当になる。

`$0.15/分` はその上に、ターンがもっと短い場合と `MAX_CONVERSATION_SEC` が上限の 900 秒まで上げられた場合の余裕を乗せた値である。コストが長さの二乗で伸びるということは、**上限の長さで較正した分単価は、それより短いすべての通話を過大計上する**。上限にとって、それは安全な向きの誤差である。

**計上は保守的に倒してある**——が、これは 2026-10-08 までは事実ではなかった。§3 を参照。端数は常に切り上げ。キャッシュ割引は見込まない。

## 2. 三つの数字が合わない（2026-10 の照合）

10 月の Vertex AI 支出について、出どころの違う 3 つの数字があり、2.7 倍ずれていた。

| 出どころ | 10 月の数字 |
| --- | --- |
| Cloud Monitoring のトークン数 × **旧**設定単価（$0.5 / $3） | ≈ **¥1,500** |
| 実際に消費された無料トライアルのクレジット（**全サービス**） | ≈ **¥3,257** |
| **Spend Cap が数えた額**（定価・クレジット前、Vertex AI のみ） | **¥4,032** |

実測トークン数（`aiplatform.googleapis.com/publisher/online_serving/token_count`、`hachicall-nao`、10-01 〜 10-08 14:03 UTC）：

- `gemini-3.8-flash` 入力 4,580,943 / 出力 2,435,521
- `gemini-3.8-live` 入力 171,765 / 出力 17,475

同じトークン数を 3 通りの単価で評価すると、3 つの数字はすべて説明がつく（150 JPY/USD）。

| 単価 | Flash | Live | 合計 | 円 |
| --- | --- | --- | --- | --- |
| 旧設定（$0.5 / $3） | $9.60 | $0.14 | **$9.74** | ¥1,460 |
| Vertex 請求額（$0.75 / $3.75） | $12.57 | $0.73 | **$13.29** | ¥1,994 |
| Vertex 定価（$1.50 / $7.50） | $25.14 | $0.73 | **$25.86** | ¥3,879 |

- **¥1,500 は我々の台帳が過小だっただけ**。旧単価は Gemini 2.5 世代のもので、3.8 Flash の定価に対して入力 1/3、出力 1/2.5 しかない。定価との比は **$25.86 / $9.74 = 2.66 倍**で、これが報告された 2.7 倍そのものである。
- **¥3,257 は別のものを測っている**。全サービスの純額（クレジット適用後の価格）で、うち Vertex AI 分は ¥1,994。差の ¥1,263 は Cloud TTS（r3 eval は全通話を音声合成する）・Cloud Run・Firestore・Cloud Storage・Monitoring など Vertex 以外である。
- **¥4,032 と計算値 ¥3,879 の差は 3.8%**。トークン実測が 10-08 14:03 UTC で切れている一方 Spend Cap は数え続けていたこと、および Live の毎ターン再課金が Monitoring のトークン数に完全には現れていないことで説明できる範囲。

### どの数字が効くのか

**¥4,032 の側、つまり定価・クレジット前の数字だけが API を止められる。** 残り 2 つは請求書と我々の見積もりで、どちらも何も止めない。

したがって台帳の単価は定価に合わせる。請求額に合わせると、**我々の算術ではアプリ側の上限が下にあるのに、Google の算術では上にある**という、唯一成立しない配置になる。そのとき先に発動するのは Google 側で、Google 側は**すでに鳴っている電話を切る**ことで発動する。

### EXCLUDE_ALL_CREDITS の罠

Spend Cap の予算は `creditTypesTreatment: EXCLUDE_ALL_CREDITS` に**強制される**。選べない。そして遮断の判定は**定価ベースの推定グロス額**で行われる。

ここから 2 つ帰結する。

1. **自己負担が 0 円でも遮断される。** 10 月の実際の持ち出しは ¥0（無料トライアルのクレジット残 ¥41,743、残り 83 日）だった。それでも Spend Cap は ¥4,032 を数え、Gemini Live を止めた。「クレジットがあるから大丈夫」は Spend Cap には通用しない。
2. **導入割引は味方にならない。** Flash の 50% 引きはクレジットとして与えられるので、Spend Cap からは除外される。割引価格で予算を組むと、Spend Cap からは倍の速さで埋まっていく。

## 3. 二つの上限の順序

**設計意図は、アプリ側が必ず先に発動すること。** そうであれば止まるのは「発信すること」で、**電話は鳴らない**。Google の Spend Cap は、アプリ側の計算が間違っていたときのための最後の網であって、通常運転で触るものではない。

| | 金額 | グロス換算 |
| --- | --- | --- |
| Google Spend Cap（`aiplatform.googleapis.com`、10 月） | ¥15,000 | $100 |
| アプリ側 `AI_MONTHLY_CAP_USD` | $70 | ¥10,500 |
| **アプリ側が実際に止まる点**（× `AI_SPEND_STOP_FRACTION` 0.9） | **$63** | **¥9,450** |
| 余裕 | | **¥5,550**（Spend Cap の 37%） |

- 為替は **150 JPY/USD** を仮定。請求アカウント `01D85A-FFC293-94B4AB` は `currencyCode: JPY` なので、Spend Cap の金額は円、我々の単価はドルで、換算は避けられない。$300 の無料トライアルが ¥45,000 相当であることと整合する。
- Google 側はアプリ側の停止点の **1.59 倍**にある。
- 為替が 180 JPY/USD まで振れても ¥15,000 = $83.3 で、$63 はなお 24% 下にある。

**$100 ではなく $70 なのは、余裕が「我々が間違っている分」のためにあるから。** 円建ての上限をドル建ての台帳で守る以上、為替は我々の管理外にある。加えて、台帳が構造的に見られない Vertex 支出が残る（プロセスが落ちた Live セッション、`aiplatform` を使う手元のスクリプト）。`AI_SPEND_STOP_FRACTION` の 10% は進行中の通話が見積もりでしかないことのための余裕で、こちらとは別枠である。

## 4. 予約と精算

台帳は Firestore の `spend/{YYYY-MM}` に月ごと 1 ドキュメント。`spentMicros`（確定した支出）と `leases`（進行中の予約）を持つ。

```
発信直前   予約を取る（取れなければ発信しない）
  ↓
通話終了   Twilio が報告した秒数で精算し、予約を消す
  ↓
解析完了   実トークン数を確定支出に足す（予約はしない）
```

**予約は原子的**。読んで判断して書くまでが 1 トランザクションなので、同時に 4 件の発信が走っても、最後の 1 件ぶんの予算を 2 人が同時に見ることはない。既存の `dialLease`（同じ通話を二重に発信しない仕組み）と同じ作法。

**予約額は最悪値**。通話は Voice Gateway の `MAX_CONVERSATION_SEC` より長くなれないので、1 通話の上限コストは発信前に分かる。最悪値を押さえておけば、たまたま何本も長引いた月が上限を超えることはない。解析の出力は入力の半分で見積もる——Gemini の推論トークンは出力として課金され、しかも数が多い（10 月の実測で出力は入力の 53%。数百語の JSON から素朴に見積もる 1 割ではない）。

**精算は冪等**。Twilio のステータスコールバックは複数回届くので、既に消えた予約に対する精算は何もしない。実績が取れなかった場合は予約額をそのまま消費したものとして扱う（不明なコストは無料ではない）。

**戻ってこない予約は書き戻さず没収する**。6 時間を超えた予約は確定支出に移す。サービスが落ちるたびに予算が増えるなら、それは上限ではない。

**解析は予約しない**。通話はもう起きているので、その解析を予算が拒否することはできない。数字を正しくするためだけに計上する。これは Gemini の**2 つの**リクエストに効く。通話後のレビューと、録音を聴く `GeminiListener`（SPK-01/SPK-03 の測定）。後者は 1 分の音声をプロンプトに持つので安くはなく、以前は台帳から完全に抜けていた。

## 5. 上限に達したとき

- 止まるのは**新しい日次見守り通話だけ**。`placeCall` が `skipped / budget_exhausted` を返し、その試行は `failure.code = budget_exhausted` として記録される。何も起きなかったのではなく、理由があって起きなかったことが残る。
- **緊急時の経路は止まらない**。R1 の検知から家族・職員への SMS と架電、会議へのブリッジは上限と無関係に動く。母親が倒れたことを家族に伝えるのを止める上限は、置く意味がない。
- **職員に見える**。キュー画面の先頭に「Check-in calls have stopped.」と理由が出る。止まった理由を聞かれるのは職員なので。

打ち切りは上限の **90%** で起きる（`AI_SPEND_STOP_FRACTION`）。残り 10% は、進行中の通話がまだ見積もりでしかないことと、Google の実請求が我々の計算と一致しないことのための余裕。

## 6. Google Cloud 側（二次防御）

アプリ側の上限はアプリが動いていることを前提にしている。請求側の上限はしていない。両方設定する。

```bash
# 請求アカウント ID は `gcloud billing accounts list` で確認する。
# 金額は請求アカウントの通貨（この請求アカウントは JPY）。
gcloud billing budgets create \
  --billing-account="$BILLING_ACCOUNT_ID" \
  --display-name="hachi-monthly" \
  --budget-amount=15000JPY \
  --threshold-rule=percent=0.5 \
  --threshold-rule=percent=0.9 \
  --threshold-rule=percent=1.0 \
  --filter-projects="projects/$GOOGLE_CLOUD_PROJECT"
```

予算アラート（`--threshold-rule`）は**通知であって遮断ではない**。

### Spend Cap は遮断する

別物として **Spend Cap** がある（Cloud Billing Budgets の機能、Preview）。こちらは実際に API を止める。このプロジェクトで対象になるのは `aiplatform.googleapis.com`（"Gemini Enterprise Agent Platform, formerly Vertex AI"、サービス ID `C7E2-9256-1C43`）。

止まり方は乱暴で、進行中の Gemini Live セッションが

```
closed: 1008 Spend cap breached for project: projects/NNN for service: aiplatform.googleapis.com
```

で切られる。2026-10-08 に本番で起きたのがこれである（issue #19、ADR 0002）。

**Spend Cap を置く場合、金額はアプリ側の上限より必ず上にする**（§3 の表）。下にあると、アプリ側は「予算はまだある」と判断して発信し続け、電話は鳴り、利用者は無音と謝罪だけを聞く。アプリ側の台帳は請求側の Spend Cap を読めないので、この食い違いはアプリ側からは一切見えない。

見えないものは防げないので、代わりに**観測した結果から判断する**仕組みを入れてある（§6.1）。

### 6.1 Voice Gateway のサーキットブレーカー

請求側の遮断であれ、クォータであれ、権限であれ、モデル ID の誤りであれ、**「全部の通話が同じように失敗する」状態は事前に知りようがない**。1 本目が失敗するまで分からない。そこで 1 本目の失敗を記録して 2 本目以降を止める。

- Voice Gateway が Live API の close 理由を `service/gateway` に書く（`packages/core/src/gateway.ts`）。
- 理由が**系統的**（spend cap / billing / quota / permission / not found / close 1008）なら、その 1 本で発信を止める。**一時的**（瞬断など）なら 3 回連続するまでは止めない。
- 止まっている間 `placeCall` は `skipped / gateway_unavailable` を返す。**電話は鳴らない。**
- 15 分（`GATEWAY_COOLDOWN_SEC`）ごとに 1 本だけ通して回復を確かめる。会話が成立したら通常運転に戻る。
- **緊急経路は止まらない。** §5 の上限と同じ理由で、同じように止まらない。
- 連絡が取れなかった利用者はトリアージキューの先頭に出る。黙って見守りをやめないために。

コストは「障害ごとに 1 本の着信」で、「1 日 3 回 × 全利用者」ではない。詳細は `docs/adr/0002-*.md`。

## 7. 評価スクリプトの支出

**10 月の Gemini 支出の約 94% は評価スクリプトで、そのどれも台帳に載っていなかった。** 10/04 と 10/05 の 2 日だけで（旧単価で）約 $9.72。通常運転は 1 日 $0.1〜0.3 である。

- `eval/run.ts` は `reviewer.review()` に `onUsage` を渡していなかった。
- `eval/r12-run.ts` は `MemoryStore` に計上していたので、ケースごとに捨てられていた。
- `eval/seed-demo.ts` は `FirestoreStore` を使っているので、最初から記録されていた。

3 本すべてが実際の台帳（Firestore）に書くようになった（`services/analyzer/eval/spend.ts`）。自分のコストを、直後に捨てる store に書き込む実行は、誰にも何も伝えていない。

**評価の実行は、日次通話と違って一律には拒否しない。** 理由は非対称性にある。400 人に架電するスケジューラは数字を読んで判断できないので、閉じる側に倒れるしかない。評価を回すのは端末の前にいる人間で、そちらは判断できる。提出は 2026-10-18 で、1 回の実行が ¥500〜1,000、締切前に何回か必要——締切直前のリハーサルを予算のために壁で止めるほうが、高くつく間違いである。

したがって：

- 実行前に必ずその月の状況を 1 行で表示する。
- **すでに打ち切り点を超えている場合だけ**停止し、数字と対処法を出す。「近い」では止めない。最後の 10% は我々の算術が間違っていたときのための余裕で、評価 1 回はそれを使い切れる唯一の操作である。そこを使い切った次に発動するのは Google の Spend Cap で、それは**鳴っている電話を切る**。
- `--ignore-budget` で続行できる。続行してもなお記録する。
- **台帳が読めないときも拒否する。** 続行すれば、それは「直した」と主張するコードが置かれた状態で元の盲目に戻ることになる。`--ignore-budget` はもともと「台帳の許可なしに使う」という意味なので、こちらも同じ旗で通る。

## 8. 設定項目

| 変数                          | 既定   | 置く場所                       |
| --------------------------- | ---- | -------------------------- |
| `AI_MONTHLY_CAP_USD`        | 70   | telephony / analyzer / api |
| `AI_SPEND_STOP_FRACTION`    | 0.9  | 同上                         |
| `GEMINI_LIVE_PRICE_PER_MIN` | 0.15 | 同上                         |
| `GEMINI_PRICE_IN_PER_M`     | 1.5  | 同上                         |
| `GEMINI_PRICE_OUT_PER_M`    | 7.5  | 同上                         |
| `GATEWAY_COOLDOWN_SEC`      | 900  | telephony                  |
| `GATEWAY_TRANSIENT_FAILURES` | 3   | telephony                  |

単価の 5 つは 3 サービスすべてに同じ値を置くこと。api は表示にしか使わないが、職員に見える数字と実際に効いている上限がずれるのは避けたい。`GATEWAY_*` は発信を決める telephony だけが読む。

### 反映する

既定値はコード側（`parseSpendSettings()`）で正しくなっているので、**再デプロイすれば何も設定しなくてもこの値になる**。以下は再デプロイを待たずに反映する場合、および**以前に古い値を手で設定していた場合にそれを上書きする**ためのもの。

`--update-env-vars` は加算で、他の変数を消さない。`infra/deploy-*.sh` が使っている `--set-env-vars` は**全変数を置き換える**ので、そちらと混ぜないこと。

```bash
REGION=asia-northeast1
SPEND='AI_MONTHLY_CAP_USD=70,AI_SPEND_STOP_FRACTION=0.9,GEMINI_LIVE_PRICE_PER_MIN=0.15,GEMINI_PRICE_IN_PER_M=1.5,GEMINI_PRICE_OUT_PER_M=7.5'

gcloud run services update hachi-telephony --region "$REGION" --update-env-vars "$SPEND"
gcloud run services update hachi-analyzer  --region "$REGION" --update-env-vars "$SPEND"
gcloud run services update hachi-api       --region "$REGION" --update-env-vars "$SPEND"
```

確認：

```bash
for s in hachi-telephony hachi-analyzer hachi-api; do
  echo "== $s"
  gcloud run services describe "$s" --region "$REGION" \
    --format='value(spec.template.spec.containers[0].env)' | tr ';' '\n' | grep -E 'AI_|GEMINI_PRICE|GEMINI_LIVE'
done
```

`hachi-voice-gateway` と `hachi-notifier` は台帳に書かないので対象外。

## 9. 検証していないこと

- **実請求との照合**。Google の invoice は依然として別物である。§2 で照合したのは Cloud Monitoring のトークン数・クレジット消費額・Spend Cap の計数値の 3 つで、請求書の明細ではない。
- **Spend Cap の計数値を直接読んだわけではない**。¥4,032 は遮断が起きた時点でコンソールに出ていた数字で、API から取得して突き合わせたものではない。計算値 ¥3,879 との 3.8% の差の内訳は推定である。
- **Live の毎ターン再課金の実測**。`$0.15/分` の根拠にした「約 15 秒のターン × 約 16 回の再課金」は、10 月の Live トークンの入出力比（171,765 / 17,475 ≈ 9.8）から逆算した推定であって、1 通話を分解して数えたものではない。詳細と導出は `docs/adr/0003-*.md`。
- **実際にアプリ側の上限に達した状態**。単体テストでは上限 $0 や $1 で打ち切りを確認しているが、本番で**アプリ側の**月額上限に達したことはまだない。請求側の Spend Cap に達した状態は本番で起きた（2026-10-08）。
- **新しい順序が本番で保たれること**。$63 で止まることと ¥15,000 で切られることの間に ¥5,550 あるのは計算であって、観測ではない。
- **為替**。150 JPY/USD は仮定である。Google が自身のドル定価を円に換算するレートは我々が指定したものではなく、一致している保証はない。
- **利用者ごとの按分**。月全体の数字しか持っていない。
- **ブレーカーが本番の障害を止めるところ**。分類とブレーカーの遷移は単体テストで確認しているが、実際の Spend Cap 遮断中に「電話が鳴らない」ことを本番で観測したわけではない。詳細は `docs/adr/0002-*.md`。
