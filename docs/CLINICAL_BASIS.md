# 判断基準の根拠

Hachi が「いつもと違う」と判断する根拠を、どの尺度のどの基準を使っているか、そして **何を主張しないか** まで含めて記す。

実装は `packages/core/src/screening.ts`（項目と領域判定）、`packages/core/src/loneliness.ts`（孤独感）、`packages/core/src/r1.ts`・`r2.ts`・`r3.ts`（3つの検知ルール）にある。

## 1. 基本方針

### 1.1 Hachi は基本チェックリストを実施しない

日本の介護予防の標準は厚生労働省の**基本チェックリスト**（25項目・7領域）で、事業対象者の判定基準も公表されている。これを使わない理由はない — ただし2つの制約がある。

1. **文言を変えられない。** 公表されたカットオフは、検証されたその文言・その選択肢・その想起期間で尋ねたときにだけ意味を持つ。翻訳も言い換えも、カットオフの根拠を捨てることになる。
2. **Hachi の利用者は英語話者である。** 日本語の原文をそのまま読み上げることはできない。

したがって Hachi は次のようにする。

- **尋ねるとき**は、英語で検証された尺度（ULS-3、PHQ-2、FRAIL）をその文言のまま使う。対応する尺度がない項目は、基本チェックリストの番号付き項目と**同じ行動について英語で尋ねる質問**を使う。
- **報告するとき**は、基本チェックリストの7領域に対応づけ、領域ごとに「回答済み項目数／全項目数」を必ず添える。
- **点数は出さない。** 「基本チェックリストで○点」とは言わない。言えば、実施していないものを実施したと主張することになる。

Hachi が出す結論は常に「この領域は専門職が正式に評価する価値がある」であって、評価そのものではない。

### 1.2 回答が足りないときは判定しない

領域判定は `meets: boolean | null` を返す。`null` は「回答が足りず、どちらとも言えない」である。

- 該当項目が閾値に達していれば `true`
- 残りの未回答項目が全て該当しても閾値に届かなければ `false`
- それ以外は `null`

栄養領域は項目11（体重減少）と項目12（BMI）の両方を要する。**項目12は電話では測れない**ので、この領域は Hachi だけでは永久に `null` であり、`missing: [12]` として明示する。黙って分母から外せば「問題なし」に見えてしまう。

## 2. 使用する尺度

| 尺度 | 項目数 | 範囲 | カットオフ | 出典 |
|---|---|---|---|---|
| ULS-3（UCLA孤独感尺度 短縮版） | 3 | 3–9 | 6以上 | Hughes, Waite, Hawkley & Cacioppo (2004), *Research on Aging* 26(6) |
| PHQ-2 | 2 | 0–6 | 3以上（感度83%・特異度92%） | Kroenke, Spitzer & Williams (2003), *Medical Care* 41(11) |
| FRAIL scale | 5（うち3問を使用） | 0–5 | 3以上で frail | Morley, Malmstrom & Miller (2012), *J Nutr Health Aging* 16(7) |
| 基本チェックリスト | 25（うち16問に対応する質問） | — | 領域別の公式基準 | 厚生労働省「介護予防マニュアル」 |

ULS-3 と PHQ-2 は電話での実施が検証されている。FRAIL scale は自己申告式で、電話での使用も報告されている。

基本チェックリストの領域基準は公式のまま実装している（運動：項目6–10のうち3項目以上、栄養：11・12の両方、口腔：13–15のうち2項目以上、閉じこもり：項目16、認知：18–20のうち1項目以上、うつ：21–25のうち2項目以上、全般：項目1–20のうち10項目以上）。

### 2.1 採用しなかったもの

- **MNA-SF**（簡易栄養状態評価表）：Nestlé の商標であり、許諾なしに実装できない。栄養は基本チェックリストの項目11と、R2の食事・水分の記録で見る。
- **Six-Item Screener / AD8 / SQiD**：認知機能の電話スクリーニングとして検証されているが、本人への見当識質問（今日は何日か等）を毎日の雑談に混ぜると、通話の性格が変わる。基本チェックリストの項目18–20に対応する質問にとどめ、より踏み込んだ評価は専門職に委ねる。
- **LSNS-6**（社会的ネットワーク）：孤独感とは別の構成概念で、6項目は毎日の通話には長い。

## 3. 尋ね方の設計

質問の仕方そのものが検知の精度を決めるため、次のように設計している（CNV-13〜CNV-15）。

**1通話2問、12日で一巡。** 24項目を2問ずつで12日。通話を問診にしないための上限であり、同時に全項目の定点観測を成立させる下限でもある。

**12という数字は7と互いに素である。** 一巡が7日や14日だと、同じ項目が毎回同じ曜日に当たる。孤独感は週末に強く出るため、曜日が固定されるとその偏りがそのままベースラインになる。12日周期なら項目は曜日を横断して移動し、曜日効果が平均化される。

**繊細な項目は1通話に1問まで、かつ通話の後半。** 孤独感とうつの質問が同じ通話に2つ重なると、雑談ではなく面接になる。項目の並び順自体をそのように組み、テストで保証している（`packages/core/test/screening.test.ts`）。

**回答は選択肢を読み上げて選ばせる。** 自由回答を後から分類すると、分類器の癖がカットオフに混ざる。選択肢は検証された文言のまま読み上げ、LLM にはその通話で実際に出した質問IDと、その質問が持つ選択肢だけを候補として渡す。返ってきた回答はコード側で再検証し、本人以外の発話に紐付いたもの、語彙にない質問ID、その質問が提示していない選択肢はすべて破棄する（`services/analyzer/src/analysis.ts` の `groundAnswers`）。推測された回答は無回答より悪い。

**暦日で回る。** ローテーションは通話回数ではなく暦日で決まるので、1週間つながらなくても同じ2問で止まらない。

## 4. 3つの検知ルール

### 4.1 R1：急な体調の異変

FAST / BE-FAST（脳卒中）と、救急の一般的なレッドフラグに対応させている。

| 検知対象 | 根拠 |
|---|---|
| 顔のゆがみ、片側の脱力、言葉が出ない | FAST |
| 急なふらつき・平衡障害 | BE-FAST の B |
| 急な視力低下・二重視 | BE-FAST の E |
| 人生で最悪の頭痛 | くも膜下出血の典型的訴え |
| 胸痛・胸部圧迫感、呼吸困難、窒息 | 救急レッドフラグ |
| 動けない・起きられない、失神、大量出血 | 同上 |

**除外が本題である。** 「火曜まで医者に会えない（can't see the doctor until Tuesday）」「なぜそう言うのか分からない（can't see why）」「眼鏡をなくした」「昨夜ひどい頭痛だったが治った」「友人が入院した」はいずれも R1 ではない。`packages/core/test/r1.test.ts` の150件はほぼこの境界を守るためにある。

頭痛は「いつもの頭痛と違う」ことが危険信号なので、"worst / terrible / blinding / thunderclap" という修飾語を伴う場合に限って検知する。修飾語のない頭痛は検知しない。

**発症時刻を一度だけ尋ねる。** 脳卒中では発症時刻が血栓溶解療法の可否を決める。救急隊が必ず尋ねる項目なので、助けを呼んだ後に一度だけ尋ね、それ以上は何も言わない（`services/voice-gateway/src/prompt.ts` の `ONSET_QUESTION`）。

### 4.2 R2：食事と水分

INTERACT の "Stop and Watch" は「食べる量が減った」と「飲む量が減った」を**別のトリガー**として挙げている。高齢者では脱水がせん妄・転倒・急性腎障害に変わる速度が、欠食が何かに変わる速度より速い。したがって水分を食事より重く見る（DET-07）。

| 状況 | 緊急度 |
|---|---|
| 食事不良 1日 | watch |
| 水分不良 1日 | action |
| 食事不良 2日以上 | urgent |
| 水分不良 2日以上 | urgent |
| 同日に食事・水分の両方が不良 | urgent（初日から） |

最後の行が重要である。食事も水分も摂れていない人は「何も口に入っていない人」であり、2日目を待つべきではない。

### 4.3 R3：話し方の変化

本人自身の過去の通話から作ったベースラインに対して、応答潜時・言い直し率・話題の一貫性などの変化量を見る。集団平均との比較はしない。風邪・入れ歯・疲労などの一時的要因と回線品質を除外条件として記録する（SPK-01〜SPK-04）。

## 5. 孤独感と家族への連絡

### 5.1 尺度が判定し、会話は文脈として添える

孤独感の判定は ULS-3 のみが行う。通話中の発言（`mood.lonely` などのタグ）や「誰かに電話してほしい」という依頼は、**尺度の点数を動かさない**。尺度のカットオフは、その質問の仕方で検証されているからである。

会話から拾える孤独感は、尺度が未完成のあいだ（利用開始からおよそ最初の2週間）に限って単独の手がかりとして扱い、`heardInCalls` として別に報告する。

判定は4つの状態を取る。

- `incomplete`：3項目が揃っていない。何も言わない。
- `settled`：カットオフ未満。
- `lonely`：カットオフ以上。
- `worsening`：前の一巡ではカットオフ未満だった、または2点以上上がった。

3点刻みの尺度で1点の上下は誤差なので、変化と呼ぶのは2点以上の上昇に限る。

### 5.2 家族に伝えるのは「変わったとき」だけ

毎巡「お母様はまだ寂しがっています」と送られる家族は、やがて通知を読まなくなる。そこで伝えるのは次の2つの場合に限る（NTF-06）。

- 初めて尺度が読めるようになり、その値がカットオフ以上だったとき
- カットオフを跨いだとき

### 5.3 同意がなければ何も伝えない

本人の気分や孤独感は、善意であっても家族に当然に伝えてよい情報ではない。本人の人生である。`Resident.consent.shareMood` に、**職員が本人から聞き取った内容として**記録されている場合にのみ送る。誰がいつ聞いたかを併せて残す。同意がなければ、スタッフ画面にその旨が明示され、家族には何も送られない。

### 5.4 文面に尺度を出さない

家族に送る文面は「もう少し人と話せるとうれしいようです。お電話いただけると喜ばれます」であって、点数も尺度名も診断語も含めない。家族に評価を求めているのではなく、電話が喜ばれると伝えているだけである。テストでこれを強制している（`packages/core/test/loneliness.test.ts`）。

## 6. 電話番号の取り扱い

本人が口頭で番号を伝えた場合、番号は **LLM の出力からではなく本人の発話そのものから読み直す**（`groundContactRequest`）。モデルが一桁書き換えても、宛先は変わらない。

番号は次のいずれでも採用しない。

- 1つの発話に異なる番号が2つ以上ある（どちらかを推測しない）
- "double" / "triple" などの倍数語を含む（聞き間違えると以降の桁がすべてずれる）
- 日本の番号として成立しない桁数（携帯11桁・固定10桁。10桁の 090 は桁落ちであり固定電話ではない）

採用した番号でも、登録済みの連絡先と一致しない限り自動送信しない。一桁の聞き間違いは、本人の名前と「一人暮らしである」という事実を他人に送ることになる。担当職員**または**登録済みの親族のいずれかが承認したときにのみ送る（NTF-05）。

## 7. Hachi が主張しないこと

- 基本チェックリストの点数、および事業対象者の判定
- 診断、病名、服薬の助言
- 尺度の結果をもって「うつである」「フレイルである」と述べること
- 回答が足りない領域について「問題なし」と述べること
- 本人の同意なく、本人の気分や孤独感を家族に伝えること
